## What the app does

- **Matrix:** sort tasks into four boxes by urgent and important: Do first, Schedule,
  Delegate, Eliminate. Unfinished tasks carry over to the next day.
- **Focus:** work on a task in 25-minute sessions (Pomodoro), with pause and resume.
- **Patterns:** see where your focus time went, and how often "urgent" tasks were downgraded
  a few days later.
- **Yours:** installable on a phone, works offline and without an account. Sign in to sync
  tasks to your own account (Supabase, protected by Row Level Security). Export any time.

Every action (task created, moved, finished, focus started, paused, abandoned) is saved as an
event. That history is what makes the analysis possible.

## The data pipeline

```mermaid
flowchart LR
  A[App · React<br/>every action saved as an event<br/>in one documented format] --> F[Daily event files]
  subgraph AF [Airflow runs these steps in order]
    F -->|load| R[(Database<br/>DuckDB)] --> D[dbt<br/>clean → model → metrics<br/>54 checks]
  end
  D --> X[Dashboard<br/>Tableau Public]
  D --> W[Weekly summary<br/>written by an AI tool]
```

1. **Source:** the app's event log, in a documented format ([data contract](docs/event-schema.md)).
2. **Load:** events go into a database, one day at a time.
3. **Clean:** duplicates removed, bad timestamps repaired, broken rows set aside and counted.
4. **Model:** SQL (dbt) turns events into metrics with written definitions, and 54 checks
   confirm the numbers are right.
5. **Report:** the metrics are exported for the dashboard. An AI tool writes a short weekly
   summary from them.

Airflow runs these steps in order, and GitHub Actions re-runs every check when the code
changes.

> **Note:** for privacy, the data in this repo is synthetic, in the same format as the app's own
> data.

## Task sync (Supabase)

Signed-in users' tasks are saved to a `tasks` table in Supabase, so they're on every device
and can be read by other tools (for example, an AI assistant that plans calendar time blocks).
The device keeps its own copy: the app stays instant and works offline. A save that fails
stays on the device, shows a "not saved" banner, and retries until it goes through.

**Schema** ([migrations](supabase/migrations/)):

| Column | Type | |
|---|---|---|
| `id` | uuid | Primary key, generated by the app |
| `user_id` | uuid | References `auth.users`; defaults to the signed-in user |
| `title` | text | |
| `quadrant` | text | `do` · `schedule` · `delegate` · `eliminate` |
| `status` | text | `open` · `done` (completed tasks are kept) |
| `task_date` | date | The day the task is planned for |
| `subtasks` | jsonb | `[{ id, text, done }]` |
| `position` | integer | Display order |
| `created_at`, `completed_at`, `updated_at` | timestamptz | |
| `deleted_at` | timestamptz | Set when deleted in the app; the row is kept |

**Security:** Row Level Security is on. Signed-in users can only select, insert, update and
delete rows where `user_id = auth.uid()`; signed-out visitors have no access. The browser
only ever has the project URL and the publishable key.

**Setup** for your own Supabase project:

1. Apply the SQL in [`supabase/migrations/`](supabase/migrations/) (SQL Editor, or `supabase db push`).
2. Copy `app/.env.example` to `app/.env` and fill in the project URL and publishable key
   (Project Settings → API). For deploys, set the same two values in `app/.env.production`
   or in your host's environment variables.
3. Run the app, choose **Sign in to sync**, and create an account.

Tests for the sync logic: `cd app && npm test`.
